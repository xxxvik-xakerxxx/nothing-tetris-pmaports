# Explicit GPUEB parent adoption candidate

Not packaged. All additions are separate from cf22166's frozen SRAM controller
and allocation audit. No existing DT, binding, APKBUILD or shared workflow is
changed. Kconfig is bool/default n. The Makefile is an external object-smoke
harness, not a shipping module.

## Parent/child integration implemented

The future real remoteproc parent explicitly calls `mt6878_gpueb_adopt_parent`
with its platform device. The adapter obtains the named `gpueb_base` resource
and invokes the real frozen full-SRAM resource owner. No second parent or
automatic device lookup by physical address is accepted. Exactly one physical
SRAM profile exists on this SoC; the registry binds it to that device identity.

Children supply an explicit parent device and their existing resource. The
adapter verifies exact GPR/mailbox slice base AND complete size, obtains a typed
controller lease and retains the parent through that lease. A matching address
alone cannot adopt the wrong parent. Prefix, overlapping, expanded and invalid
resources are rejected. Child resource snapshots are bounds/lifetime metadata,
not raw mappings or power/firmware authorization.

Parent removal is serialized under the registry mutex, rejects active leases,
and calls the frozen controller's explicit destroy. It retains registry entry,
full claim and parent reference after quarantine even with all leases returned.
Unknown partial start is forwarded to the real owner; no software OFFLINE or
reset result clears it. Callers serialize final lease release against users and
must retain a failed-to-remove parent. No platform remove refusal is invented.

## Existing callers migrated, hardware path closed

`caller-migration.patch` is generated by `prepare_migration.py` against exactly
the existing 0120 mailbox/session sources plus 0122's failed-boot retention.
The generator checks zero-fuzz/zero-offset prerequisites. Static tests also
compare the stored candidate patch and apply it with no fuzz or offsets.

- Session: removes the independent GPR resource claim/map and adopts that window
  via `rproc->dev.parent`. Its release returns the parent lease only after the
  existing boot-attempt quarantine guard. Shared reserved RAM remains a separate
  existing resource; it is not invented as SRAM backing.
- Mailbox: only the MT6878 variant requires parent adoption. It acquires its
  existing data-window resource from `pdev->dev.parent`, never falls back to an
  overlapping independent claim, and checks the hardware gate before clock
  preparation, IRQ setup or mapping. Other SoC variants keep their existing path.
- Remoteproc: there is still no real MT6878 GPUEB platform remoteproc driver.
  0123 is only request_firmware staging. The adapter supplies the concrete parent
  resource ingress that such a driver must call; it does not fabricate a start,
  successful attach or parent object. Existing sibling DT nodes are not silently
  reparented. Without an explicitly registered matching parent, adoption defers
  (or returns EOPNOTSUPP with candidate config disabled).

`mt6878_gpueb_adoption_io_gate` always returns EOPNOTSUPP after a valid resource
check, or the underlying lifetime/quarantine error. Mailbox/session refuse to
fall through even if that gate were accidentally changed to return zero.
There is no raw mapping export and no actual MMIO/start procedure in this
candidate. The next real owner patch must migrate bounded MMIO and IRQ lifecycle
under unified ownership, then replace the closed caller boundary as one reviewed
transaction. Do NOT enable this candidate expecting a functioning mailbox.

This is resource and caller integration, not a solution to the firmware upload
span mismatch or physical OFF. No new ready flag, callback-based pretend power
proof, rail, upload length, padding, clock/reset write, or firmware command exists.

## Independent CI gates

Static: `python3 patches/gpu/test_gpueb_sram_adoption.py`.

Native: `sh patches/gpu/run_gpueb_sram_adoption_ci.sh`, CI=true. The fixture
includes the actual frozen SRAM core/adapter and the actual new adoption source.
Mock platform resources exercise explicit parent identity, duplicate adoption,
wrong/prefix/overlapping slices, child-held removal refusal, closed hardware
gate, retained full claims and immutable output after quarantine. It also runs
the frozen SRAM native tests. ASan/UBSan remain enabled. Fixture-only disposal
of quarantined mocked allocations is not a production OFF/recovery path.

Kernel objects: `sh patches/gpu/sram-adoption/smoke-kernel-ci.sh`, CI=true with
TETRIS_KERNEL_TREE and TETRIS_KERNEL_OUT set to the prepared ARM64 tree/output.
Use the CI toolchain environment. It builds frozen SRAM core/adapter, adoption,
and both migrated caller objects in a temporary external tree with generated
public headers. It neither changes shipping config nor builds/loads a module.

Main integration required: run those two CI harnesses on the next snapshot.
Do not add this candidate patch or Kconfig to APKBUILD/DT yet. A passing object
build is not a parent bind, BOOTREADY, functioning transport or physical OFF.
